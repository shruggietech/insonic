e:T18f9,<h1 id="brand-documentation-and-releases">Brand, documentation and releases</h1>
<h2 id="upstream-brand-authority">Upstream brand authority</h2>
<p>The <a href="https://brand.shruggie.tech/insonic/guidelines/brand-essentials/">insonic brand</a> belongs to upstream <code>shruggietech/shruggie-brand</code>. The integrated formal kit is insonic 1.0.0 built with BrandBuilder 3.0.1. Governed bytes live under <code>brand/kit/</code>, with the consuming repository's receipt in <code>brand/lock.json</code>.</p>
<p>The kit's consumer contract, enforcement guidance, tokens, named logos, licenses and manifest are authoritative. Product copy uses <code>insonic</code> and <code>A ShruggieTech project</code>. Local code binds semantic tokens and asset references rather than recreating artwork. Brand adoption preserves product requirements.</p>
<ol>
<li>A maintainer manually runs the freshness check.</li>
<li>Find the latest formal upstream release containing the insonic kit.</li>
<li>Compare its brand and builder versions with the local lock.</li>
<li>When an update is requested, download the archive and checksums.</li>
<li>Verify the archive digest, paths and full manifest.</li>
<li>Stage the exact kit and integration receipt.</li>
<li>Replace the integrated kit, rolling back on failure.</li>
<li>Review the diff and consumer conformance.</li>
</ol>
<p><code>npm run brand:check</code> is read-only and requires network access. <code>npm run brand:update</code> adopts the latest newer formal kit. <code>npm run brand:verify</code> checks byte integrity offline. The tools reject corrupted archives, unsafe paths, immutable-version drift and downgrades. Discovery uses official release assets. A newer BrandBuilder kit can require adoption even when the brand version is unchanged.</p>
<p>Freshness checking is outside ordinary CI, and application startup never downloads branding. Follow upstream semantic, glyph and consumer-conformance guidance when changing a UI. Exact bytes alone do not establish visual conformance.</p>
<h2 id="synchronized-documentation-and-schemas">Synchronized documentation and schemas</h2>
<p>Markdown under <code>docs/&lt;version&gt;/</code> is the documentation authority. <code>docs/versions.json</code> defines available versions and navigation. The root <code>VERSION</code>, software release, documentation version and <a href="/docs/v0.0.0/contracts/">master JSON Schema</a> share the same version. The schema's individual record definitions carry their declared version inside that release contract. Upstream Cueson retains its own versioned schema.</p>
<p>Build the website, downloadable schemas and offline documentation from the exact release tag. Retain older version routes and immutable schema identities. <code>/docs/</code> selects the latest published release. The public root route is a product landing page; <code>/docs/</code> is the versioned documentation. <code>site/out/</code> contains the full static website, including that landing page, local Mermaid diagrams and brand assets. Readers need no production Node server or remote font/diagram CDN.</p>
<p>The GUI includes <code>site/offline/</code>, the documentation-only export from the same tagged build. It excludes the public landing page and retains the matching documentation, changelog, schema resources and local assets. A release manifest records documentation/schema versions, source revision and hashes. Offline help uses installed bytes and stable relative links without a network or development server. Publish the matching site artifact and promote the default version only after release publication succeeds.</p>
<p>Each release records a CLI/GUI capability matrix, including advanced or experimental CLI features awaiting GUI controls. Core operations share the runtime and aim for parity. Adapter protocols, database migrations, model formats and upstream dependencies record their compatibility separately within the synchronized release.</p>
<p>Prefer backward and forward compatibility where practical. A breaking change remains possible when needed; document its affected interfaces and migration in the <a href="/docs/v0.0.0/changelog/">master changelog</a> and brief release highlights. Do not silently reinterpret incompatible data.</p>
<p>For every major release, rescan the complete documentation for technical terms and refresh the <a href="/docs/v0.0.0/glossary/">glossary</a> with precise definitions, primary learning references and links to the local pages using each term most heavily.</p>
<h2 id="changelog-and-highlights">Changelog and highlights</h2>
<p>The documentation site renders root <code>CHANGELOG.md</code> as the <a href="/docs/v0.0.0/changelog/">changelog</a>, preserving one master record. Released documentation freezes the tagged file at <code>docs/v&lt;version&gt;/references/CHANGELOG.md</code>; the build requires and renders that snapshot. It follows <a href="https://keepachangelog.com/en/1.1.0/">Keep a Changelog</a>. Add work under Unreleased; at release move entries into a dated version section and update comparison links. <a href="https://semver.org/spec/v2.0.0.html">Semantic Versioning</a> describes releases and compatibility.</p>
<p>Release notes contain brief highlights, major migration actions and known material limitations. Do not paste full changelog sections. End with a link to the master changelog at the release tag.</p>
<h2 id="release-sequence">Release sequence</h2>
<ol>
<li>Start from reviewed source with green required checks.</li>
<li>Align the software, documentation, JSON Schema and changelog versions.</li>
<li>Build native packages with the CLI, dependencies and documentation.</li>
<li>Verify the inventory, checksums and dependency notices.</li>
<li>Publish the immutable tag and brief release highlights.</li>
<li>Promote the matching static documentation and schemas.</li>
<li>Receive versioned user observations as issues.</li>
</ol>
<p>Package matrices include CLI-only and GUI-with-CLI options for macOS, Linux and Windows. Sign/notarize platform packages using configured credentials and tooling. The release manifest identifies native libraries, Cueson, media tools, optional workers and their digests/licenses. User-selected model downloads remain separate assets.</p>
<p>The static export is portable to ordinary static hosting; its host and domain are deployment configuration.</p>
