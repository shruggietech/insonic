32:T3ac2,<h1 id="optional-first-run-setup">Optional first-run setup</h1>
<p>Setup offers a guided route from a new library to its first import. It is optional: skip a stage, choose Set up later or use the ordinary workspace/import commands at any time. Reopen Setup from Settings to continue with the same accepted choices. CLI and desktop use shared versioned state and the same backend, processing, service and import operations.</p>
<p>Local defaults use filesystem artifacts, a SQLite catalog and a LadybugDB graph. Creating a library and importing media require no account, API key or model download. Processing and connected services are separate elections. Current installation prerequisites still apply; see <a href="/docs/v1.1.0/desktop/#native-package-layouts">CLI and desktop installation</a>.</p>

Setup completion never gates other commands.</p>

</code></pre></details></figure><h2 id="choose-a-location">Choose a location</h2>
<p>The suggested path is the platform user-data directory followed by <code>libraries/My voice archive</code>. Edit it before accepting. Location preview reports the selected path, existing library state, control/artifact/cache locations and observed capacity at the nearest existing directory without creating the destination. Installation files and library data have separate ownership; setup rejects a new library inside the application installation.</p>
<p>Control files hold workspace identity and catalog configuration. Managed artifacts contain accepted media, derived content and model bytes according to the elected storage profile. Disposable caches/materializations support work and playback. A remote storage choice can put artifacts elsewhere while retaining local control and scratch files. Metadata, media and model growth depends on later selections; the initial preview reports unknown estimates rather than inventing a total. Normal worker/model preparation previews provide their own observed requirements. See <a href="/docs/v1.1.0/storage/">storage</a> and <a href="/docs/v1.1.0/processing-setup/">local processing setup</a>.</p>
<p>An existing library is opened with its existing identity and profiles. Setup does not overwrite it or convert fresh provisioning into migration. Use the documented backup/migration operations when moving accepted data to different backends.</p>
<h2 id="start-through-the-cli">Start through the CLI</h2>
<p>Every setup command is noninteractive and supports <code>--json</code>. Use contextual help for the installed input contracts. Setup location and bootstrap-draft commands work before workspace selection.</p>
<ol>
<li>
<p>Preview the suggested location, or supply an explicit path:</p>
<pre tabindex="0" aria-label="Code example"><code class="language-text">insonic setup location --json
insonic setup location &quot;YOUR_LIBRARY_DIRECTORY&quot; --json
insonic setup draft show --json
</code></pre>
</li>
<li>
<p>Write <code>setup-draft.json</code>. Replace <code>YOUR_LIBRARY_DIRECTORY</code> with the chosen path and use the revision returned by <code>setup draft show</code> (zero for an unsaved draft). Omitted profiles elect the local defaults:</p>
<pre tabindex="0" aria-label="Code example"><code class="language-json"><span class="hljs-punctuation">{</span>

<p>For alternate backends, the draft's <code>plan</code> accepts a <code>backend-plan</code> or its normalized workspace configuration. Use <a href="/docs/v1.1.0/storage/#configure-and-preflight-backends">complete backend planning and preflight</a> to check the selected services before provisioning. <code>setup provision</code> accepts <code>--credential-backend native|vault|session</code> and <code>--secret-input</code>; protected values come from stdin using the existing bootstrap channel. Keep values out of the draft and command arguments. The draft retains its nonsecret credential-backend election; an explicit provision override saves that election before creating the library. Preserve the saved normalized plan when retrying provisioning. Bootstrap drafts retain the most recent 64 request receipts; older stale retries report a conflict without repeating effects.</p>
<h2 id="save-and-resume-a-library-journey">Save and resume a library journey</h2>
<p><code>setup show</code> reads current state without starting workers or downloads. If no journey was saved, it supplies defaults alongside current library observations. <code>settings setup</code> is the readback/reopening alias. <code>setup save --input FILE</code> changes bounded journey metadata only; it cannot provision backends, create a pipeline, download models or import media.</p>
<p>A save file contains <code>expected_revision</code> and <code>state</code>. State includes <code>status</code> (<code>active</code>, <code>deferred</code> or <code>completed</code>), <code>current_stage</code>, exactly five unique stage records and <code>choices</code>. Stage IDs are <code>workspace</code>, <code>backends</code>, <code>processing</code>, <code>services</code> and <code>import</code>; their saved states are <code>pending</code>, <code>completed</code> or <code>skipped</code>. <code>choices</code> contains <code>processing_mode</code> (<code>none</code>, <code>local</code>, <code>connected</code> or <code>custom</code>) and optional selected <code>pipeline_id</code>/<code>pipeline_revision</code>. Start with the returned state and copy each current <code>observations[stage]</code> SHA-256 proof into that non-skipped stage before making the intended change; only skipped stages may omit it. See <code>setup save --help</code> for the complete template.</p>
<p>Use the observed revision when saving and a new request UUID for each new intent. Repeating the same immutable save with the same UUID reconciles the accepted result. A response distinguishes its accepted revision from potentially newer current state; replay does not restore old choices over newer saves. A stale save or changed input under an existing request ID returns a conflict. Read current state and decide the next change without overwriting the accepted revision.</p>
<p>Configured profiles, model records and durable work retain their own authority and retry identities. Deferring, skipping or closing setup preserves these effects. Use Jobs or <code>work cancel</code> to cancel a selected job, and its supported retry operation to resume interrupted work. Moving a library or restoring a portable copy requires fresh destination observations; a saved completion marker alone cannot establish current readiness.</p>
<h2 id="readiness-and-credentials">Readiness and credentials</h2>
<p>The final summary distinguishes configured choices from usable capabilities and links the relevant Import, Settings and Jobs actions. <code>setup readiness</code> explicitly requests the shared task-specific processing checks using the saved pipeline election, or the generic readiness input when no pipeline is selected. A failed transcription, diarization or training prerequisite does not remove ready admission-only import. Missing environments, model bytes, devices and adapters name their corrective action. See <a href="/docs/v1.1.0/processing-setup/">local processing readiness</a>.</p>
<p>Connected-service discovery inspects metadata without loading a model or electing a route. Its separate synthetic test can exercise the selected route. A registered credential reference, a saved configuration, successful authentication and task usability are different observations. Desktop forms name the credential task in plain language, accept protected values and generate an opaque reference; only the reference enters configuration. CLI values use the <a href="/docs/v1.1.0/secrets/">protected credential channel</a>. Setup state rejects credential values, signed URLs, arbitrary settings and unknown fields.</p>
<h2 id="offline-use-and-recovery">Offline use and recovery</h2>
<p>The same setup guide is bundled with the installed documentation. Local library creation and admission use packaged companions and need no network. Managed environment/model preparation requires its elected sources to be available; offline inputs and exact existing model snapshots use the normal processing preparation controls. Skip these stages when their prerequisites are unavailable and continue with import.</p>
<p>Setup retains stage progress across client closure and can be reopened from Settings or CLI. A changed configuration can require a new observation proof; a failed effect remains inspectable in Jobs.
