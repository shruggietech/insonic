17:T5da5,<h1 id="grounded-answers-evidence-and-context">Grounded answers, evidence and context</h1>
<p>Evidence preparation collects current source spans for a question, explains their selection and provenance, and fits source-preserving extracts into an explicit context budget. <code>answers prepare</code> does not call an inference provider. <code>answers request</code> uses the elected provider to produce a structured answer, checks its citations against the exact visible context and current source authority, and retains verified answer bytes. Citation validity and faithful quotations do not establish that a quotation logically proves a paraphrased claim.</p>
<p>These commands are available in builds containing the evidence/context capability. Published package availability follows the <a href="/docs/v1.3.1/changelog/">release notes</a>. Dedicated desktop controls follow; the shared runtime already accepts the same requests as the CLI. Ordinary <a href="/docs/v1.3.1/graph/">search and graph queries</a> remain available independently.</p>
<h2 id="request-a-grounded-answer">Request a grounded answer</h2>

The <code>insonic-http</code> adapter implements the structured answer contract; native <code>ollama</code> uses its configured service root and exact model. An existing encrypted credential reference can be supplied as <code>credential_id</code> for authenticated routes.</p>

<p>Admission returns a durable <code>work_id</code>. Work reports retrieval, context, synthesis, validation and publication phases, selected model/route, budgets, independent families and limitations. Successful work returns <code>answer_id</code> and <code>package_id</code>. A wait timeout ends only the wait. Explicit cancellation prevents later acceptance. Retry of failed, cancelled or interrupted work creates a new linked attempt with the original frozen configuration; prior history remains readable. Generic <code>work retry</code> uses the same behavior for answer work. A new <code>answers request</code> elects changed settings.</p>
<p>Instead of <code>configuration</code>, select a saved <code>pipeline_id</code> and optional <code>pipeline_revision</code>. A pipeline can contain only <code>answer_synthesis</code>, or combine it with processing/training configuration. With neither configuration nor pipeline specified, the current saved assistance settings supply the election. Admission freezes that election, including its nonsecret configuration digest. No provider, model or route is silently substituted.</p>
<p>The provider receives only the question, bounded visible cue prefixes, authoritative references, family identities, conflicts and limitations. Source instructions remain source data. Generated claims declare <code>kind: quote</code> or <code>kind: paraphrase</code>; quote claims must equal one of their cited quotations. A response can contain at most 128 claims and 128 distinct references. The provider response is bounded to 512 KiB, the complete serialized request to 128 KiB, and the retained answer to 1 MiB. An oversized request fails explicitly rather than silently dropping evidence.</p>
<p>Answer synthesis supplies a complete typed JSON Schema, including exact version and package identity, structured citation references and string-valued limitations. Native local Ollama receives that schema as its structured output format. Schema conformity does not establish source authority or semantic support.</p>
<p><code>max_repairs</code> accepts zero or one and defaults to one. Invalid structured output can consume that single repair using locally generated reasons, a bounded field/type/constraint diagnostic where available, and the same complete schema, evidence and route. Diagnostics exclude rejected provider values and arbitrary validator text. The optional <code>repair_detail</code> contains a generated <code>reason</code> and a <code>validation</code> object with a sanitized field pointer, expected type or constraint/bound where available; it does not contain the rejected response. Both calls and their validation share the elected provider deadline (30 seconds by default, maximum 60 seconds). Exhaustion produces an explicit insufficient answer without accepted unsupported claims. Authentication, routing and transport failures remain durable failures. Whole-work execution has a separate 180-second bound; ordinary retrieval retains the bounds below.</p>
<p>Candidate bytes are hash-verified before acceptance. The catalog accepts the answer and terminal work state together only while source identity, work generation, lease and cancellation state still match. Restart reconciles retained candidate bytes before any provider rerun. Inspection separates immutable historical bytes from current freshness and acceptance. An artifact published before failed or cancelled acceptance is never presented as an accepted answer. Export contains source references and safe provider identity, without provider endpoints or credential values.</p>

<p><code>prepare</code> returns a retained package UUID when persistence succeeds, the evidence/context package, current source freshness, cache reuse and measured work. <code>show</code> and <code>export</code> read the same verified immutable package and report current freshness separately. Use <code>--json</code> for the complete versioned response and redirection. Human output puts state, freshness, graph limitations, context omissions and continuation before details.</p>
<p>A package can be <code>complete</code>, <code>partial</code> or <code>insufficient</code>. Completeness describes evidence preparation, not successful answer synthesis. Cancellation returns a non-success error with the available partial observation; an unretained attempt has no package UUID. Missing or stale graph publication remains visible even when current catalog cues are usable. Preparation never implicitly publishes or rebuilds the graph.</p>
<h2 id="bounded-retrieval">Bounded retrieval</h2>
<p>The selected SQLite or PostgreSQL catalog is authoritative. A bounded source-identity scan establishes the current recording, document, mapping, date, provenance and assertion identity. Cue pages select one recording before expanding its transcript; the runtime does not export and hydrate the whole library. Exhausting the identity allowance reports <code>source_identity_budget</code>; narrow <code>filters.media_ids</code> or elect a larger allowance before proceeding.</p>
<p>Text, entity and concept filters select seeds. Media, current speaker, recording-calendar and exact source-interval filters remain enforced during neighboring-cue and relationship expansion. Without a text filter, question terms affect ranking rather than excluding all other text. Entity IDs are normalized graph identities. Concept IDs distinguish subject, relation and object roles, so equal labels in different roles are not silently merged.</p>
<p>LadybugDB and ArcadeDB use the same bounded neighborhood contract. Each graph page pins workspace, target, generation and sequence, supports relationship kinds and direction, and continues by edge identity. A four-edge route can connect a source cue through its assertion, a shared concept and another assertion to a second recording's cue. Every admitted cue is resolved against its current catalog document. Stale/missing graph references are excluded or diagnosed; disconnected sources do not become related merely because their text is similar.</p>

Graph and context omissions remain explicit; rerun with a larger elected allowance when those details are needed. <h2 id="provenance-and-reproducible-ranking">Provenance and reproducible ranking</h2>
<p>Exact source digests and accepted canonicalization origin facts establish source families. Known stream/channel identity and overlapping source intervals establish overlap groups. Unknown cross-recording stream identity does not prove overlap. Equal text never proves common origin. Distinct observed source families retain the possibility of an unknown shared upstream origin; their count is not an acoustic independence certification.</p>
<p>Repeated imports, overlapping cues and repeated extracted assertions retain inspectable source members while receiving independent-family and overlap-coverage credit once. Reported/quoted assertions do not add independent support. Independent sources with similar wording remain distinct. Opposite polarity for the same asserted subject, relation, object and conditions is recorded as a conflict; different conditions or a different object alone do not prove contradiction.</p>
<p>Ranking uses question-term overlap, distinct-family credit, overlap coverage and opposing-family conflicts. Its total is four times relevance, plus twice independence, plus coverage, plus twice contradiction. Ties use evidence identity. Conflicting evidence remains visible rather than being suppressed by a confidence score. Contradiction detail is bounded to 500 pairs and 64 KiB, with a visible exclusion when more detail exists. No answer confidence is inferred from this score.</p>
<h2 id="context-and-cache-authority">Context and cache authority</h2>
<p>Context contains cue extracts, sections of sixteen source cue ordinals, recording nodes and a cross-recording node. Higher levels organize links to underlying evidence; they are not additional sources. Cue text is an exact source prefix of at most 1,024 Unicode code points, shortened further when necessary. Condensation and omitted evidence are explicit. A later reader can resolve each source ID through the retained package.</p>
<p>Byte accounting includes the entire serialized context, question, hierarchy, source links and accounting fields. Token units conservatively use UTF-8 bytes of that envelope; they do not claim to reproduce a provider's tokenizer. The <code>source-extract-v1</code> contract rejects invented summary text. No context node has stronger or independent authority than its source cues.</p>
<p>Cache identity binds workspace, effective question/scope/budgets, current source/document/speaker/date/provenance/assertion identity, graph observation, elected provider/model, nonsecret configuration digest, prompt identity and summary contract. Provider identity is optional for preparation and contains no endpoint or credentials. Preparing context makes no provider request.</p>
<p>Packages use the configured filesystem or S3 artifact storage and SQLite or PostgreSQL catalog. Immutable bytes are hash-verified, explicitly retained, and indexed through a workspace-scoped compare-and-swap pointer. Cache metadata and artifact writes do not change semantic source identity. A corrupt pointer or failed byte verification is a diagnosed miss; recovery creates a new publication instead of overwriting historical bytes. Lost responses and concurrent pointer writes are reconciled against persisted state.</p>
<p>Inspection reports <code>current</code>, <code>stale</code> or <code>unknown</code> source freshness. Source replacement, mapping/date changes or incompatible configuration prevent reuse. Historical packages remain readable; inspection never rewrites their original observations. The package's usage records work at serialization, while the response's usage includes current request checks performed after publication or during cache reuse.</p>
<h2 id="claims-and-citations">Claims and citations</h2>
<p>An answer envelope names its retained <code>package_id</code>, version, state and claims. A <code>supported</code> claim requires citations. <code>unsupported</code>, <code>uncertain</code> and <code>conflicting</code> claims require an explicit uncertainty reason and cannot appear in a completed answer. Each citation binds the evidence member, exact reference and a faithful source quote. Revisions, cue ordinals and microsecond intervals use decimal strings so large values remain exact in JavaScript clients. Untimed sources omit the interval.</p>
<p>Validation checks every citation against the retained package and current catalog evidence, including multiple quotes from the same cue. Forged workspace/document/mapping/timing identities, stale sources and invented quotes are rejected. Passing citation validation establishes source provenance, not semantic entailment, factual truth or completed answer generation. See the generated <a href="/docs/v1.3.1/contracts/">JSON contracts</a> for complete request, package and answer-envelope shapes.</p>
