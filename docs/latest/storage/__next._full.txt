<h2 id="application-and-user-data">Application and user data</h2>
<p>Install executable code in ordinary platform application locations. Never store user media inside the installed application directory or the source checkout. App upgrades replace code and bundled docs while preserving user workspaces and settings. An uninstall removes application code; deletion of user data is a separate explicit choice.</p>

<p>These locations describe user-space choices, not promised installer registration. Windows ZIP installation changes no PATH entry; the Linux desktop helper writes a launcher. Desktop + CLI includes a usable CLI beside the application; the ZIP helper changes no global PATH entry. System-wide installation is optional; normal local use does not require elevated privileges.</p>
<h2 id="three-independently-selected-profiles">Three independently selected profiles</h2>
<p>A workspace selects an artifact storage profile, catalog profile and graph profile. The default is local filesystem, SQLite and LadybugDB. Generic S3-compliant providers, including user-run filesystem-backed S3 endpoints, PostgreSQL and ArcadeDB are supported alternatives. A local S3 endpoint still uses the S3 adapter; its underlying filesystem is not exposed as a second source of truth.</p>
<p>Profiles contain adapter ID/version, nonsecret options and credential references. Current explicit workspace contracts support the declared backend choices; workspace show and doctor expose configuration and diagnostics. Shared CLI/desktop backend plans, bounded preflight and explicit fresh-workspace provisioning are implemented. <a href="/docs/v1.0.1/setup/">Optional first-run setup</a> guides these operations, saves progress and preserves accepted profiles. Credentials use the <a href="/docs/v1.0.1/security/">secrets service</a>. Preserve the selected workspace/profile identity across configuration and the established migration/backup workflow for existing data. Selecting a backend does not require repeated human approval for normal writes.</p>

<p>No backend is silently substituted after failure. The local defaults need no server administration. Remote alternatives require the user's configured service and credentials; their installation/deployment guidance is separate from normal desktop installation.</p>
<h2 id="catalog-operation-and-transfer">Catalog operation and transfer</h2>
<p>The shared catalog provides revision-checked settings and immutable typed metadata/date records, scoped speaker/corpus/training/model relationships, exact current speaker profiles, durable work/attempts, expiring workspace ownership and ordered graph events. Processing, elected training and matching publish through fenced acceptance; graph records project current catalog authority. SQL and connection details stay inside the adapter. Audit instants retain ISO text and exact signed nanoseconds; reports/options use lossless JSON alongside typed relationship columns.</p>
<p>SQLite opens the selected local file with foreign keys on every connection, immediate writer transactions, WAL and full synchronization. PostgreSQL uses a dedicated schema, short workspace-row ownership transactions and server time sampled after locking. Both accept operation IDs and intent digests atomically with revisions and receipts; retrying the same intent reconciles an unknown acceptance outcome. An obsolete attempt cannot renew or publish after expiry, cancellation or takeover. Outbox consumers receive only the next unacknowledged target event and acknowledge under current fenced ownership.</p>
<p><code>catalog show --json</code> reports selected catalog identity, schema and revision. <code>catalog export &lt;file&gt;</code> writes a consistent versioned logical snapshot into a new private file; it refuses to overwrite existing output. <code>catalog restore &lt;file&gt;</code> accepts an empty catalog with the same workspace identity, verifies the snapshot digest and relational constraints, restores in one transaction and expires imported claims. Preserve the original workspace configuration/identity while selecting an empty destination catalog. Export does not copy artifact bytes or switch configured profiles. Restore and explicit migration require the local owner to be stopped; an idle owner exits automatically.</p>
<p><code>jobs history &lt;job-id&gt; [after-generation] --json</code> returns up to 128 attempts and a nullable <code>next_generation</code> cursor. Pass that cursor as <code>after-generation</code> to read the next page. <code>--request-id &lt;UUID&gt;</code> lets clients retry a start, cancel or retry operation after a lost response with the same identity and intent. Artifact bytes remain in their configured store.</p>
<p>File restore validates the input stream through a private disposable spool and decodes those validated bytes. Export and restore share the same supported representation without a fixed file-size cap; decoded records and transaction resources scale with catalog size. Restored graph checkpoints require the matching acknowledgement receipt, intent digest, event identity and ordered accepted outcome. When selecting a different catalog location, advance its profile revision or select a new profile ID so the imported immutable configuration history stays intact.</p>
<p>An optional profile <code>expected_backend_version</code> constrains the selected catalog's actual engine version. Use an exact dotted version or comma-separated comparisons such as <code>&gt;=18,&lt;19</code> (up to eight comparisons). The constraint is preserved in immutable profile revisions and snapshots; an incompatible engine prevents startup.</p>
<p>For PostgreSQL, configure host, port, database, dedicated schema, TLS mode and optional CA/credential reference in the catalog profile. <code>verify-full</code> verifies certificate and hostname; <code>local</code> accepts literal loopback addresses, localhost pinned to 127.0.0.1, or a Linux Unix socket. <code>insecure</code> explicitly elects remote plaintext. A remote host formerly labeled local now receives a correction; configuration is never silently rewritten. <code>catalog migrate</code> provisions the selected schema using migration authority. Runtime opening of an existing schema needs ordinary catalog data permissions, not schema-creation rights. No PostgreSQL environment connection defaults or pgpass routing override the selected profile, and no backend is silently substituted.</p>
<p>The runtime resolves PostgreSQL credentials through an injected provider or the explicitly selected <code>INSONIC_SESSION_CREDENTIALS</code> transient mapping of credential IDs to username/password objects. Resolved values stay in memory and never enter snapshots, jobs, receipts or diagnostics. Persistent native/encrypted credential storage remains a separate secrets-service implementation. A missing configured credential returns unavailable rather than falling back to plaintext persistence or a different catalog.</p>
<h2 id="workspace-and-artifact-layout">Workspace and artifact layout</h2>
<p>A workspace has a stable identity and a user-selected local control directory. First run suggests a location and estimates capacity. Several workspaces can share downloaded base models while keeping media, speaker models and catalogs logically separate. A remote artifact store or catalog does not eliminate local scratch, decoding materializations or the control directory.</p>
<p>The optional nonsecret <code>credential_namespace_id</code> identifies this control directory's credential store and defaults to the workspace ID. Portable restore preserves the destination's effective credential namespace while adopting the source catalog identity, so its configured native/vault credentials remain usable after restart. Credential values and their encrypted store remain local and are not copied into the bundle.</p>

<p>Filesystem keys are relative to the managed root. Explicit external file references remain distinguishable from managed copies. Moving a local workspace rebinds its root and validates bytes without rewriting Cueson documents. Reject traversal and ambiguous portable paths. Follow symlinks only under the documented import policy, without allowing archive extraction outside its destination. Arbitrary filenames and provider URLs are never interpolated into a shell command.</p>

</code></pre></details></figure><h2 id="artifact-adapter-and-s3-guarantees">Artifact adapter and S3 guarantees</h2>
<p>The source-buildable CLI implements managed filesystem and generic S3 publication through the shared runtime. <code>artifacts publish &lt;file&gt; &lt;kind&gt;</code> stages and hashes a regular local file, records a durable publication attempt and verifies completed bytes before admitting its artifact/location records. <code>--request-id &lt;UUID&gt;</code> makes publication retryable; changed content or kind under that ID conflicts. The response <code>id</code> is also the publication ID used by subsequent commands. CLI paths resolve in the calling process before IPC, so spaces and Unicode do not depend on the owner's launch directory.</p>
<p><code>artifacts show &lt;id&gt;</code> reads catalog status without contacting the store. <code>artifacts verify &lt;id&gt;</code> checks current readable bytes. <code>artifacts reconcile &lt;id&gt;</code> resumes a pending operation or admits an already completed, verified object after an uncertain response. Pending operations retain a private staged source and multipart upload/part receipts. <code>artifacts abort &lt;id&gt;</code> aborts a pending multipart attempt; already admitted artifacts require explicit retirement. Configured operations do not require per-file review. These advanced CLI controls precede dedicated desktop storage controls, which will wrap the same runtime interface.</p>
<p><code>artifacts materialize &lt;id&gt; [max-bytes]</code> returns a verified private cache path and lease. The default per-file admission bound is 10 GiB; the optional positive byte ceiling explicitly overrides it for that operation. Publication has no application-wide file-size cap and streams staged bytes. Storage/provider quotas and local disk errors remain operation failures. Materialization and publication claims renew during external work, including recovery reads. Leases last 30 seconds; consumers must run <code>artifacts lease-renew &lt;id&gt; &lt;lease-id&gt;</code> while using a cache file and <code>artifacts lease-release &lt;id&gt; &lt;lease-id&gt;</code> when finished. Expired or released leases cannot be revived; obtain a new materialization. <code>artifacts cache-prune &lt;id&gt;</code> atomically fences expired leases before deleting their cache files, retaining cleanup state until deletion is reconciled.</p>
<p>Publication and inspection responses contain bounded identity/location receipts plus multipart, reference, lease and event counts. Complete operational journals remain in catalog snapshots. Restore binds each journal to its latest publication receipt and validates immutable admission evidence before expiring imported authority. Abort refuses to abandon a pending journal when final bytes already exist; reconcile that publication before retiring its admitted object.</p>
<p><code>artifacts retain &lt;id&gt; &lt;reference-id&gt;</code> pins bytes and <code>artifacts release-reference &lt;id&gt; &lt;reference-id&gt;</code> releases that explicit pin. Original media, current metadata, valid current preparation and durable models retain their bytes through structural catalog associations. Superseded computed reports/transcript derivatives/preparation lose obsolete references and enter recoverable retirement. <code>artifacts retire &lt;id&gt;</code> requires no retention references or live materialization leases and a one-minute grace period from verified admission. It atomically blocks new references/materializations before deleting the exact recorded object/version. An uncertain deletion remains retiring and can be retried. Artifact and location identities retain immutable admission history in receipts; successful retirement updates both the publication journal and typed location availability in one catalog transaction. A live catalog cannot bypass the retirement barrier through generic record admission.</p>
<p>Artifact lifecycle journals and their receipt relationships are included in catalog snapshots. Catalog schema 2 upgrades schema 1 transactionally while preserving records, revisions and receipts. Validated schema-1 logical snapshots remain accepted. Restore expires publication/materialization authority and preserves pending retirement barriers; it neither copies staged/cache files nor artifact bytes. Pending publication can be reconciled from remote final bytes; resuming an unfinished upload requires its verified private staged input at the original workspace or an explicit matching source retry.</p>
<p>S3 configuration selects endpoint, bucket, prefix, region and addressing style. Remote endpoints require HTTPS with normal certificate validation. Explicit HTTP URLs are supported for localhost and literal loopback/private network addresses; other DNS names require HTTPS. Credential mode resolves an opaque credential ID to an in-memory object containing <code>access_key</code>, <code>secret_key</code> and optional <code>session_token</code>. Explicit environment mode selects <code>AWS_ACCESS_KEY_ID</code>, <code>AWS_SECRET_ACCESS_KEY</code> and optional <code>AWS_SESSION_TOKEN</code>; anonymous mode sends no credentials. No ambient credential chain overrides credential or anonymous mode. Buckets must already exist. Provider errors are redacted, and profiles, receipts and snapshots contain no credential values. Doctor reports implemented operations and configured capabilities; it does not claim remote reachability from successful configuration alone.</p>
<p>Managed filesystem access is confined to an opened root. Input files are opened atomically without following the final symlink/reparse point, checked through the opened handle for regular-file status and copied from that handle. Unix uses nonblocking no-follow opens so a substituted FIFO cannot stall validation. Generated immutable keys reject traversal and ambiguous portable names. Managed keys include workspace identity and exact storage profile revision so separate catalogs sharing a root or bucket cannot retire each other's objects. Filesystem publication links a fully flushed private stage without replacement, then flushes directory ancestry on Unix or final-file metadata on Windows before admission. Recovery repeats that durability step. Windows uses the documented <a href="https://learn.microsoft.com/en-us/windows/win32/fileio/file-caching">file metadata flush</a> behavior. Hardware must honor these flush requests; automated checks do not simulate physical power loss.</p>
<p>S3 uses unique publication keys, explicit resumable multipart identity and independent readback SHA-256; ETags are part receipts rather than content identities. The journal records completion intent before PUT or multipart completion. Abort observes uncertain visibility for a bounded interval and keeps an indeterminate completion pending; an absent upload ID alone never proves its bytes were not completed. Exact range headers and returned length are checked. Conditional-create support is reported only where established; the generic S3 baseline uses unique keys. Pinned fixture evidence covers common operations and multipart resume/abort; production authentication and provider-specific visibility/version behavior require that endpoint's qualification.</p>
<p>The artifact adapter contract includes <code>Capabilities</code>, <code>Stat</code>, <code>OpenRange</code>, <code>PublishImmutable</code>, <code>Materialize</code>, <code>Verify</code> and <code>DeleteUnreferenced</code>. Publication returns a receipt with storage profile, final key/version, digest, size and verification method. Capabilities declare conditional create, ranged reads, multipart/resume, provider checksum semantics, version IDs and read-after-write behavior. They are probed or qualified for the selected implementation, not inferred from an S3-compatible label.</p>
<p>Amazon S3 documents <a href="https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html">conditional writes</a> and <a href="https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel">strong read-after-write consistency</a>; generic providers must establish their own equivalent behavior. Multipart ETags are <a href="https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html">not whole-object content hashes</a>. insonic computes its own digest and records provider checksums separately.</p>
<p>For filesystem output, stage on the destination filesystem, hash and flush, then atomically publish without replacing a different object. For S3, complete an upload at an immutable key and verify readable final bytes before committing a catalog reference. Use conditional create when verified; otherwise use a unique attempt key so no existing admitted object is overwritten. Content deduplication is a catalog decision. Where trustworthy end-to-end provider checksums are unavailable, read back and hash the completed object. For a provider with delayed visibility, wait within a bounded policy and leave the publication pending if visibility cannot be proven. Object listings alone never determine whether an artifact exists.</p>
<p>Adapters support streaming and bounded local materialization for tools needing seekable files. Unknown remote results are reconciled by exact key/version and digest. Incomplete multipart uploads retain attempt identity and can be resumed or aborted. Cleanup waits for active leases and a grace period, then atomically claims retirement in the catalog while checking retention references. That claim prevents new reference/materialization admission until retirement is reconciled. Delete only the claimed object key/version/generation; a read-then-delete reference check alone is insufficient. Do not reuse remote keys while an earlier delete can still finish. Filesystem publication/deletion shares the lifecycle lock. Historical provenance retains retired/missing availability, and source media and durable model outputs retain independent identity. Superseded computed reports and preparation are removed through explicit current-result retirement, not retained as hidden alternatives.</p>
<h2 id="catalog-adapter-and-postgresql-ownership">Catalog adapter and PostgreSQL ownership</h2>
<p>The catalog contract provides typed reads, transactional <code>CommitRevision</code>, immutable evidence admission, job claim/renew/complete, workspace lease acquisition/renewal, outbox claim/acknowledgement, migrations, consistent snapshot export and restore. SQL is confined to each backend implementation. Both backends enforce the <a href="/docs/v1.0.1/schema/">same logical constraints</a>, pagination and revision behavior. SQLite enables foreign keys for every connection, uses its transactional writer model and keeps its file on a supported local filesystem. A live SQLite catalog is not placed in S3 or shared as a network object.</p>
<p>PostgreSQL uses a dedicated configured database/schema and least-privilege application role. Setup distinguishes runtime rights from migration/administration rights. Remote TLS verifies the service identity by default; a configured local service can explicitly use its local transport. PostgreSQL documents <a href="https://www.postgresql.org/docs/current/libpq-ssl.html">certificate/hostname verification</a>. Host credentials, passwords and full connection strings with secrets do not enter exports or logs.</p>
<p>Each catalog query includes workspace scope. Transactions use expected revisions to reject lost updates. Workspace-scoped coordinator, migration and projection leases store owner ID, generation and expiry; PostgreSQL uses server time and short row-locking transactions to acquire/renew them. Jobs may use its <a href="https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE">queue-oriented <code>SKIP LOCKED</code> support</a>, followed by recorded claim generations. Leases are not a database-wide lock. Work outside a transaction must prove its generation again before publication; paused or disconnected workers cannot acknowledge a replacement worker's result.</p>
<p>Transactions never remain open during audio decoding, AI calls or model training. Retry serialization/deadlock failures only around idempotent transactional operations. A lost commit response triggers operation-ID reconciliation. PostgreSQL selection requires the full catalog path, including restoration and failure recovery; it is not considered supported after only a successful connection test.</p>
<h2 id="portable-backup-commands">Portable backup commands</h2>
<p>The <code>backup</code> commands are advanced offline maintenance operations over the shared catalog and artifact contracts. They acquire the workspace owner lock rather than starting processing workers. An active owner returns a conflict; close its clients and allow the idle owner to exit before maintenance. Dedicated desktop backup controls are not yet available.</p>
<ol>
<li>Create a self-contained bundle with <code>insonic backup create BACKUP_DIRECTORY --workspace WORKSPACE --json</code>. The destination is a new private directory. A repeated request uses the same <code>--request-id UUID</code> for reconciliation.</li>
<li>Inspect completion and authority with <code>insonic backup show BACKUP_DIRECTORY --workspace WORKSPACE --json</code>; verify available bytes with <code>backup verify</code>.</li>
<li>Select an independently configured empty destination workspace and use <code>insonic backup restore BACKUP_DIRECTORY --workspace DESTINATION --json</code>. Validation precedes catalog and workspace configuration activation.</li>
<li>Rebuild the destination graph from accepted evidence using the selected graph backend; imported checkpoints do not assert destination currency.</li>
</ol>
<p>Self-contained bundles carry a logical catalog snapshot, exact immutable artifact identities and verified digest-addressed bytes. They retain canonical audio, current embedded Cue JSON, external mappings, intentional rosters, model references and durable trained output lineage. Historical receipts needed to validate provenance remain, while transient inference inputs and superseded derived byte payloads are excluded. This differs from <code>catalog export</code>, which copies catalog data only.</p>
<p>Use <code>backup create BACKUP_DIRECTORY --mode reference-only</code> only when retaining the original artifact store. That bundle records exact object versions and source dependency, and persistent backup-owned references block ordinary cleanup. Provider retention remains independently necessary. <code>backup release BACKUP_DIRECTORY</code> releases that backup's catalog pins; it does not imply the original store is available or remove the bundle directory. Missing bytes, invalid hashes or relations, unsafe paths, incompatible schemas and nonempty restore targets fail without replacing accepted target authority. Credentials and engine scratch are not backup assets; configure destination access separately.</p>
<p>An interrupted preparation can leave retained pins before a completed bundle exists. Use <code>backup release BACKUP_UUID</code> with the original request ID to release that receipt-proven backup's references. Arbitrary manual retention IDs are not accepted as backup recovery identities. A completed same-ID retry reconciles the self-contained capture pins; reference-only pins remain until explicit release.</p>
<p>An interrupted restore retains private destination upload progress. A committed catalog remains fenced if configuration activation fails, even after its operational lease expires. Retry the same bundle with the same destination profiles to reconcile activation. A different bundle or changed destination configuration cannot take over that pending restore.</p>
<p>Incomplete local acquisition inputs are private source-workspace dependencies, not portable assets. Backup leaves the source operation unchanged and replaces those unaccepted input pointers in its generated catalog authority with a receipt-backed interrupted-input marker. Restored work requires a fresh explicit input rather than reopening an old local path. The manifest retains both the untouched source capture digest/revision and generated portable catalog digest/revision; accepted audio, metadata and model provenance remain intact.</p>
<p>Processing, speaker training/matching and model-dependency work also excludes originating tool paths, transient recognition hints and compiled input copies. Receipt-backed portable elections retain model identities, configured stage routes and settings. Automatic recovery builds an ephemeral invocation using the destination's selected processing tools and accepted catalog context; rebound absolute paths never become portable job data. Standard tool roles can select the destination platform's validated binaries. Custom adapter and support files require their exact hashes in the destination's <code>.insonic/processing-tools.json</code> <code>portable_files</code> array, with entries containing absolute <code>path</code> and lowercase <code>sha256</code>. Missing bindings leave work pending for automatic retry after configuration becomes available. No per-item approval or cancellation is introduced, and completed lineage remains retained.</p>
<p>Saved pipeline configurations and historical training options receive the same portable binding treatment, preserving logical revisions and output lineage for future elections. Model-dependency recovery does not require unrelated processing tools. Numeric parameters retain their exact JSON integer values during rebinding.</p>
<p>An absolute custom-adapter argument dependency must have a declared support-file hash so its destination binding preserves the elected input. An undeclared local dependency returns <code>unsupported_capability</code> before bundle publication or source mutation; declare its exact support identity before retrying capture. Ordinary flags and configured hosted routes retain their existing meaning.</p>
<h2 id="capacity-migration-backup-and-recovery">Capacity, migration, backup and recovery</h2>
<p>Before a managed copy, derivative or training job, estimate local scratch and final-store capacity separately. For object services with no capacity API, report that distinction and handle quota failures. Cache cleanup never removes leased inputs. Base model removal lists dependent presets. Trained speaker models are durable artifacts with their own retention rules and are not grouped into downloadable-model cache cleanup.</p>
<p>Backups bind a consistent logical catalog snapshot to an artifact manifest at one catalog revision on SQLite and PostgreSQL. Native database backups, such as SQLite's <a href="https://www.sqlite.org/backup.html">online backup API</a>, do not alone back up media/model bytes. A self-contained backup copies and verifies the referenced immutable bytes into retained backup storage. A reference-only backup records exact object versions and its dependence on the original store. Catalog retention references prevent insonic cleanup from deleting pinned objects for the backup's lifetime; provider retention must independently preserve those versions. A version ID alone identifies bytes without guaranteeing their availability. Restore resets graph checkpoints and rebuilds materialization from accepted evidence on the selected graph backend. Schema compatibility, hashes and external references are validated before activating a restored workspace.</p>
<p>Backend migration exports typed records and immutable manifests, validates destination constraints and bytes, then switches profiles at a recorded catalog revision. Pause affected writes under the workspace migration lease. Retain the old authority until the destination is verified; migration never creates two writable catalogs. Exact SQL, index and graph DDL differ by backend, while logical schema version and application behavior remain aligned. Unsupported newer schemas open with an actionable incompatibility message and are not downgraded silently.</p>
<p>Catalog and artifact adapters must pass interrupted publication, reconnect, stale-lease and round-trip migration checks on filesystem/SQLite and S3/PostgreSQL. Graph adapters apply the corresponding acceptance matrix. Normal pull-request checks use bounded fixtures; version-qualified backend integration checks run for the affected adapter without forcing every prose edit through heavyweight services.</p>
<h2 id="configure-and-preflight-backends">Configure and preflight backends</h2>
<p>The three roles have equivalent CLI and desktop plans: filesystem root or S3 endpoint/bucket/prefix/region/addressing/authentication; SQLite path or PostgreSQL host/port/database/schema/TLS/CA/credential; LadybugDB path or ArcadeDB endpoint/database/credential/dialect. Optional expected backend versions remain explicit profile constraints. Defaults need no key. Credentials are opaque references, with newly entered values supplied through protected input before the initial catalog connection.</p>
<ol>
<li>Write a nonsecret <code>backend-plan</code> document with <code>schema_version: &quot;1.0.1&quot;</code>, <code>display_name</code> and elected <code>profiles</code>. Omit roles to use local defaults. <code>workspace plan --help</code> includes the complete schema and an input template.</li>
<li>Run <code>insonic workspace plan --input backend-plan.json --json</code>. Save the returned <code>result.configuration</code> as the generated plan; its workspace/profile identities are the retry identity.</li>
<li>Run <code>insonic workspace preflight DIRECTORY --input generated-plan.json --json</code>. Use <code>--secret-input</code> for a protected stdin message containing newly entered <code>session</code> values keyed by the plan's credential IDs. Preflight registers no credentials and changes no files, schema or objects.</li>
<li>Elect <code>insonic workspace provision DIRECTORY --input generated-plan.json --credential-backend native --secret-input --json</code>. The protected channel can contain <code>session</code> username/password objects for PostgreSQL/ArcadeDB, access_key/secret_key/session_token objects for S3, and a vault passphrase when vault is elected. Values do not belong in the plan or arguments.</li>
<li>Inspect the exact configuration and readiness. Identical committed-plan retries reconcile success; different input conflicts. A populated existing workspace is preserved; transfer uses the explicit backup/migration workflow.</li>
</ol>
<p>Desktop workspace creation and Settings offer fields for all six choices, generated opaque credential references, separate preflight/provisioning actions, current selection inspection and cancellation. Native/vault credentials persist locally; session credentials live in the runtime owner and must be supplied again after restart. S3 environment and anonymous modes remain explicit choices.</p>
<p>Readiness dimensions distinguish syntax, reachability, transport, authentication and target/schema compatibility. Filesystem/SQLite/LadybugDB preflight inspects paths without opening databases or creating WAL sidecars; schema, filesystem locality and writes remain untested. PostgreSQL performs authenticated read-only catalog inspection. S3 HeadBucket proves limited bucket access and may not distinguish denied access from a missing target; it proves no object-write permission. ArcadeDB checks authenticated database existence without provisioning; projection schema remains untested. Optional write-test objects are not used.</p>
<p>Provisioning retains a private nonsecret <code>provision-intent.json</code> before the first credential/backend mutation. Failed and completed attempts reconcile only with that exact configuration and credential-backend choice; a newly generated different plan, missing receipt or changed persisted credential selection conflicts. Corrected newly entered credentials for its elected references can be supplied again through the protected channel. Before publishing workspace configuration, provisioning observes non-mutating access to the selected S3 bucket when elected (it does not create buckets or prove object write permission), initializes the selected graph, validates its expected version and binds its workspace owner. Graph failures remain failures instead of being deferred after success. LadybugDB relative paths resolve from the workspace root, matching runtime graph selection.</p>
