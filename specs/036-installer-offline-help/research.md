# Research: S036

## 2026-10-17 decisions

- Use a modeless action-display Progress dialog before ExecuteAction, native SetProgress to Progress and ActionText to Text subscriptions. Add rollback/generation action text. Reject simulated progress and guessed remaining time. Source: [MSI progress authoring](https://learn.microsoft.com/en-us/windows/win32/msi/authoring-a-progressbar-control).
- Preserve one -1 success, -2 cancellation and -3 failure sequence entry. Freeze/elect install/upgrade/change/repair/remove identity for terminal/ready wording. Terminal pages use one Finish/Close action including Esc; progress Cancel requests confirmed engine cancellation and rollback. Sources: [sequence table](https://learn.microsoft.com/en-us/windows/win32/msi/installuisequence-table), [EndDialog](https://learn.microsoft.com/en-us/windows/win32/msi/enddialog-controlevent), [Dialog cancellation](https://learn.microsoft.com/en-us/windows/win32/msi/dialog-table).
- Share an installed-help resolver with actual version/entry validation. Windows uses the operating-system HTML association with absolute UTF-16 file path and no shell parameters. Existing same-SID limited-token handling dispatches elevated invocations without an elevated fallback. Linux uses direct xdg-open argv, hidden/redirected noninteractive I/O and bounded dispatch. Wails BrowserOpenURL rejects file URLs and returns no error, so it is unsuitable for installed help. Sources: [ShellExecuteInfo](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-shellexecuteinfow), [Wails browser](https://wails.io/docs/reference/runtime/browser/).
- Documentation starts unchecked and is fresh interactive success only, independent of the existing checked client launch. Maintenance/upgrade/removal, failure, cancellation and unattended modes suppress both fresh-install choices. A failed help opening warns the user without reclassifying committed installation.
- Retain restricted dialog capture as complementary evidence. Add real full-UI MsiInstallProductW workers with passive external UI forwarding (return 0), owned HWND automation, event/phase observations and actual 0/1602/1603 native results. Never use unknown dialog clicks or source-only assertions as native proof. Source: [external UI forwarding](https://learn.microsoft.com/en-us/windows/win32/api/msi/nf-msi-msisetexternaluiw).
- Reuse installed package/native browser harness and disposable Windows actors. Verify actual activation, installed version, local resources/navigation offline, Unicode/spaces and opening errors. Cache/reuse clones and never parallelize competing MSI transactions. Existing qualification integrity gates remain mandatory.

Alternatives considered: simulated progress, generic terminal pages, application-private popup, forced browser, shell-built HTML commands, elevated fallback and attended owner verification were rejected against explicit acceptance criteria.

- Refined decision: desktop uses a controlled embedded help frame with no popup, sharing DocumentationManifest validation with the MSI file opener. This allowed issue alternative avoids elevated desktop browser dispatch and permits native packaged content/resource/navigation checks on both hosts. Installer still uses the invoking user HTML association. No scope reduction.
