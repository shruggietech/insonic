# Feature Specification: v1.0.3 exact-main acceptance and publication

**Feature Branch**: `codex/060-v103-publication`
**Created**: 2026-10-29
**Status**: Specified
**Input**: Owner-authorized S060: execute the recommended patch acceptance/publication under Spec Kit autopilot, automatically push/open its official evidence PR, complete CI and at most two Codex rounds, and reserve that PR merge for the owner. The owner explicitly authorizes publication from accepted main while the evidence PR remains open.

## User Scenarios & Testing

### User Story 1 - Receive a patch proven on its exact bytes (Priority: P1)

A user receives the reviewed patch whose retained package has completed the maintained real CPU processing journey and fresh processing after a self-contained restore.

**Why this priority**: A passing source test cannot qualify different rebuilt archives or establish fresh restored inference.
**Independent Test**: Bind candidate source, archive and executable identities to successful original and fresh-restored processing receipts.

**Acceptance Scenarios**:

1. **Given** reviewed, green main at 72098446d435aa1e3d6d6726a9f07e04e0b227a6, **When** the publication candidate is built, **Then** all supported package variants, applicable installers and matching documentation carry version 1.0.3 and that clean source identity.
2. **Given** the retained exact Windows CLI package, **When** real CPU acceptance runs, **Then** all maintained required processing and fresh-restored matching/provenance checks pass with the original library path withdrawn.
3. **Given** accepted package bytes, **When** publication proceeds, **Then** those same retained bytes are published without rebuilding or transferring acceptance to different archives.

### User Story 2 - Download one coherent official release (Priority: P1)

A user can obtain the official v1.0.3 patch and matching current documentation while older released contracts remain available.

**Why this priority**: Publication, package identity and deployed documentation must agree.
**Independent Test**: Compare the accepted manifest and original assets with the published release, completed documentation deployment and public resources.

**Acceptance Scenarios**:

1. **Given** a qualified complete candidate, **When** v1.0.3 is published, **Then** its immutable tag identifies the accepted main source and every official asset matches the retained manifest.
2. **Given** the published release, **When** documentation is promoted, **Then** its exact completed deployment and public content identify 1.0.3 with all six product download choices and retained historical routes/schema authority.
3. **Given** partial upload or deployment failure, **When** recovery is performed, **Then** the actual resulting state and failed evidence remain explicit and unchanged accepted bytes are reused.

### User Story 3 - Review independently retained delivery evidence (Priority: P1)

The owner reviews a concise evidence PR with completed qualification, publication and review receipts, while retaining control of the PR merge.

**Why this priority**: Workflow artifact expiry and source/publication identity changes must not erase the delivery proof.
**Independent Test**: Independently recover retained receipts, inspect final checks/reviews and verify bounded cleanup plus the unmerged PR state.

**Acceptance Scenarios**:

1. **Given** completed candidate, processing and publication phases, **When** evidence is retained, **Then** source/archive/executable/deployment identities, separate timing and any failures can be independently recovered outside workflow expiry.
2. **Given** the final evidence PR, **When** handoff occurs, **Then** applicable CI is green, all arriving actionable findings are resolved within at most two Codex rounds, owned scratch is removed and the PR remains open and unmerged.

### Edge Cases

- A rebuilt archive differs despite identical source; earlier CPU acceptance does not apply.
- Current main advances during the evidence slice; publication remains bound to the selected reviewed source unless a deliberate new candidate is qualified.
- Candidate documentation carries snapshot status instead of publication-target authority.
- Managed CPU prerequisites are unavailable, changed or incomplete; preparation must finish and verify before qualification starts.
- Restore preserves old results but fresh destination inference/matching fails.
- Existing tag/release, partial upload, asset mismatch, concurrent Pages update or public verification failure requires state-specific recovery.
- A product/tooling repair is needed before publication; unmerged evidence-branch code cannot become a trusted-main release.
- GUI acceptance must remain on an isolated hosted desktop and local children must remain hidden/headless.

## Requirements

### Functional Requirements

- **FR-001**: The complete publication-target candidate MUST use reviewed main 72098446d435aa1e3d6d6726a9f07e04e0b227a6, clean source authority and matching 1.0.3 software, documentation and schema identities across supported packages and applicable installers.
- **FR-002**: The exact retained Windows CLI package MUST complete maintained real CPU processing and fresh-restored inference/matching acceptance, including provenance/integrity and original-path withdrawal.
- **FR-003**: Complete candidate assets and original receipts MUST be retained outside workflow expiry before qualification/publication or a full rerun; acceptance MUST remain bound to their unchanged archive/executable identities.
- **FR-004**: Official v1.0.3 publication MUST use the accepted main tag and those same accepted bytes, verify the complete remote asset set before becoming public, and provide concise highlights ending with the exact-tag master changelog link.
- **FR-005**: Matching original release documentation MUST be promoted to the existing destination and independently verified against its exact completed deployment, live content and six official product download identities.
- **FR-006**: Historical release assets, documentation/schema authority and exact original evidence exemptions MUST remain unchanged. No unmerged product repair may acquire trusted-main publication authority.
- **FR-007**: All local command execution MUST remain hidden/headless, interactive checks MUST remain isolated from the owner desktop, and owned fixtures MUST be confined and removed without changing owner libraries or writing into Downloads.
- **FR-008**: Existing preparation/qualification accounting, 1800-second qualification target, 3600-second hard limit, finalization reserve and substantive checks MUST remain mandatory; ordinary product deadlines and intentionally short injected expiry clocks MUST remain unchanged.
- **FR-009**: Compact durable evidence MUST distinguish candidate, real CPU/fresh-restored acceptance, publication, deployment, public verification and PR CI/review identities, including any failed attempts and unverified dimensions.
- **FR-010**: The official automatically pushed evidence PR MUST finish with green applicable checks, every arriving actionable review resolved within at most two Codex rounds, clean owned output and no merge. Publication from accepted main is authorized while this PR remains open.
- **FR-011**: Broader acoustic quality, GPU/OCR, authenticated external services, owner-installed behavior and physical exhaustion MUST NOT be inferred from these receipts; remaining dimensions MUST stay explicit under the broader audit.

### Key Entities

- **Publication candidate**: Version, reviewed source, original assets, inventories, notices and platform qualification receipts.
- **Processing acceptance**: Bound archive/executable identities, verified prerequisites, real original/destination outcomes, provenance and timing.
- **Published release**: Immutable tag/source, complete remote asset identity and final publication state.
- **Public documentation proof**: Original released archive, exact completed deployment and checked resource/download identities.
- **Evidence PR**: Spec Kit identity, recoverable delivery receipts, final checks/reviews and owner-controlled unmerged state.

## Success Criteria

### Measurable Outcomes

- **SC-001**: Every supported package and applicable installer/documentation asset passes maintained identity, inventory and qualification checks at version 1.0.3 and the selected reviewed source.
- **SC-002**: Every maintained required real CPU and fresh-restored acceptance stage passes on the exact retained package, with complete integrity/provenance and cleanup evidence.
- **SC-003**: All published asset identities and every required public documentation/download check match the accepted original candidate and exact deployment.
- **SC-004**: One clean official evidence PR is handed off unmerged with green applicable CI, zero unresolved actionable findings, at most two Codex rounds and independently recoverable phase-specific receipts.

## Assumptions

- The release version is already prepared; no product feature, dependency, schema or version migration is intended.
- Existing maintained release, qualification, managed model and documentation tools are reused. Demonstrated evidence-PR CI scheduling and read-only website verification repairs may be included without changing selected product or publication source.
- The evidence PR may contain operational records without changing the already-reviewed release source. Any demonstrated prerequisite repair must reach reviewed main before its effects can be published.
- Original candidate bytes remain retained through verified publication; rebuilding cannot inherit their CPU acceptance.
- The broader audit remains open; no attended owner-desktop acceptance gate is introduced.
